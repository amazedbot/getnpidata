## 1. What this project is

**Goal:** a public website and REST API for searching every US healthcare provider (medical, dental, etc.) in the
CMS NPPES registry. Example query: "all Chiropractors in Suffolk County, NY", shown as a paged list and downloadable
as CSV.

```
CMS NPPES files + other public datasets ──► Npi.Loader (scheduled) ──► MySQL: full raw data (system of record)
                                                                         + the search projection and the tables built on it
                                                                                     │
                                                       Npi.Web: site + /api/v1 (reads the projection)
```

- **Today:** the loader and MySQL (`workplace`) run on the owner's PC, and the site runs locally for LAN use.
- **Production (docs/PRODUCT_PLAN.md Phase 2, not started):** the loader runs on a schedule in Azure against an Azure
  database, and the site on App Service (§2 "Azure loading"). The PC stays the development and test environment.

- **Data source:** https://download.cms.gov/nppes/NPI_Files.html; files at `https://download.cms.gov/nppes/<file>.zip`.
- **Repo:** https://github.com/amazedbot/getnpidata (`origin`). It is the only remote; never push anywhere else.

## 3. History: the legacy VB loader

### 3.1 What it was

The repo started as a VB.NET (.NET Framework 4.8.1) console app. In the owner's environment it loaded NPPES files
into MySQL; its load branches were half commented out. Stage 0 removed unrelated sibling projects, a nested old copy,
a ClickOnce key and stale files. Stage 1 ported the loader to C#, checked parity against the VB-loaded data, and
deleted the VB project. It remains in git history before the `stage-1-loader` merge, under `legacy/getnpidata-vb/`.

### 3.2 Known defects of the VB loader (each has a regression test; code comments cite them as "legacy defect #N")

1. **Silent row loss:** each CSV line was used as a *format string*; lines with `{` or `}` threw and were dropped.
2. **Column shifting:** values were split with quote awareness, then re-joined with commas *without re-quoting*, so a comma inside a value shifted the columns.
3. **No retry after failure:** a file was logged in `downlog` *before* processing, so a crash skipped it forever.
4. **False success:** download exceptions were swallowed and reported as "Successfully Downloaded".
5. **NULL never equals NULL:** the `other_names` / `practice_locations` dedupe compared nullable dates with `=`, so re-runs inserted duplicates.
6. **Deactivation report:** the zip *name* was passed to the Excel reader, and exactly 2 header rows were skipped by assumption.
7. **Case-sensitive file matching:** `"_FileHeader"` vs `"_fileheader"`.
8. **Old file naming / widths:** V1 names and widths; V2 widened first-name and legal-business-name fields.
9. **Weekly before monthly:** older weeklies could overwrite newer data (no `Last_Update_Date` guard).
10. **Unsafe SQL:** file and table names concatenated into SQL.
11. **Site outage during monthly load:** `TRUNCATE npidata` before the reload left the table empty.
12. **Minor:** shadowed connection string, meaningless counters, unused helpers, a DEBUG `Console.ReadLine()`.

## 4. Source data facts (verified against the CMS page and real files, Oct 2026)

- **V1 retired 03/03/2026.** Only V2 files are published. Accept only `_V2` names.
- Files on `NPI_Files.html` (match by regex, case-insensitive, on the href file name):
  - Monthly full: `NPPES_Data_Dissemination_<MonthName>_<YYYY>_V2.zip`, ~1.1 GB zipped, roughly 10 GB of CSV unzipped
  - Weekly incremental: `NPPES_Data_Dissemination_<MMDDYY>_<MMDDYY>_Weekly_V2.zip` (~6–8 MB; the page keeps about 4)
  - Monthly deactivations: `NPPES_Deactivated_NPI_Report_<MMDDYY>_V2.zip` (contains an .xlsx)
- Links are single-quoted relative hrefs with a `./` prefix (`href='./NPPES_…_V2.zip'`).
- Each data zip contains `npidata_pfile_*.csv`, `othername_pfile_*.csv`, `pl_pfile_*.csv`, `endpoint_pfile_*.csv`, matching `*_fileheader.csv` files and a Readme PDF. Match inner names case-insensitively. Endpoints are loaded too (`endpoints`, Stage 5.5 item 1).
- **CSV format:** `\n` line endings, every field double-quoted, dates `MM/DD/YYYY`. Per the Readme, double quotes inside values are replaced by single quotes, so no escaping occurs. The data file's header equals its `_fileheader.csv`. The header row is the source of truth for column order.
- **Header → DB column rule:** replace each run of non-alphanumeric characters with `_` and trim `_` (`Provider Organization Name (Legal Business Name)` → `Provider_Organization_Name_Legal_Business_Name`). All 330 `npidata` columns match in order, given these aliases (`HeaderMapper`):
  - the suffix `_If_outside_U_S` is dropped (the full name would also exceed MySQL's 64-character limit);
  - V2's `Provider Sex Code` → `Provider_Gender_Code`;
  - `pl_pfile`'s `Provider Secondary Practice Location Address- Address Line 1/2` → `Provider_Secondary_Practice_Location_Address_Line_1/2`.

  An unmapped header fails the load; new CMS columns need a migration.
- **Field lengths (V2 Readme):** LBN and other organization name 100, first/last names 35, middle 20, credential 20, addresses 55, city/state 40, postal 20.
- **Deactivation report:** one `.xlsx` with a title row, a header row, then NPI (text) + date (text `MM/DD/YYYY`). It is the **full current list** (355,330 NPIs on 2026-09-14, back to 2005), not a delta.
- **NPPES has no county field.** County comes from the ZIP crosswalk (§6.3).

## 6. Database design

**Local MySQL** (database `workplace` on the loader PC) holds the full raw data and the search projection.
In Azure (Phase 2), the loader will run against an **Azure Database for MySQL** holding the same data (§2 "Azure
loading"); it requires TLS (`SslMode=Required`) and firewall rules (see `deploy/azure.md`). utf8mb4 everywhere, InnoDB.

### 6.1 Raw tables (local only)

| Table | Notes |
|---|---|
| `npidata` | 1 row per NPI, all 330 CSV columns, **all TEXT** utf8mb4 except the `NPI CHAR(10)` PK (migration 002). Raw dates are kept as text; empty → NULL. Adds `Is_Deactivated TINYINT` and `Loaded_From`. No secondary indexes (search uses the projection). InnoDB's worst-case row-size check rejects 330 columns even as TEXT, so DDL creating or altering it runs with `innodb_strict_mode=OFF`, and the loader's DB user needs `SESSION_VARIABLES_ADMIN`. Real rows always fit (~7.3 KB at most) |
| `other_names` | from `othername_pfile`. No unique key: the loader **replaces** rows (whole table monthly, per NPI weekly), which removes defect #5 by construction |
| `practice_locations` | from `pl_pfile` (secondary locations), surrogate `ID` |
| `nppes_deactivated_npi_report` | NPI, deactivation date. **Replaced in full** by each report (staging + RENAME), so reactivated NPIs drop out |
| `downlog` | (003) `filename` UNIQUE, `kind` (Monthly/Weekly/Deactivation), `file_date`, `status` (Downloading/Loading/Completed/Failed; VB-era rows = `Legacy`, which does not count as done), `started_at`, `completed_at`, `rows_loaded`, `error` |
| `extractlog` | zip, extracted file, rows |
| `schema_migrations` | version, name, sha256, applied_at; written by `Npi.Loader migrate` |
| `*_staging` | per-load staging tables, created `LIKE` the target, dropped after the swap |

**Deactivation flag rule** (`Deactivations.ApplyAsync`):
- **When it's set:** `Is_Deactivated = 1` when the NPI has a deactivation date (the report date, else `NPI_Deactivation_Date`) and no `NPI_Reactivation_Date` on or after it. An empty `NPI_Deactivation_Date` is filled from the report.
- **When it's recomputed:** for that week's NPIs after every weekly; after a monthly or deactivation report, for the NPIs queued in `deactivation_pending` before its swap (095, speed item 10): a monthly's NPIs whose row differs from the stored one (`Source_Hash`) or whose deactivation or reactivation date does (found in the same pass as the monthly's change queue), a report's NPIs it adds, drops or redates. The queue is emptied only after the flags are applied, so a load stopped in between is caught up by the next one. A first load, or more than 500,000 queued NPIs, recomputes every row (~1 min).
- **Date comparisons** use `YYYYMMDD` strings built with SUBSTRING, because `STR_TO_DATE` errors on malformed values in strict SQL mode.

**Baseline schema:** the owner's backup (2026-10-07) is captured in `db/migrations/nppes/001_baseline.sql`, with caveats in
`db/migrations/README.md`. It used V1 widths and latin1 for several tables; migrations 002–006 fixed that. The
NPPES code tables (`entity_types`, `gender_codes`, `state_codes`, `country_codes`, …) came with seed rows.
Unrelated or obsolete tables (`animals`, `dicomhosts`, `taxonomy_codes_old`) are left alone; dropping them needs the
owner's OK.

- **Change detection:** `row_hash` = MD5 over the provider's columns **and** all its taxonomy/location/other-name rows, ordered by content, so a change in a child row alone still changes the hash.
- **Build process:** `project` builds all five tables in `*_staging`, checks ≥ 95% of the current provider count, and swaps them in with one RENAME. `run` rebuilds when `data_version.projected_at` is older than the newest completed downlog or reference load.
- **Indexes after loading (speed item 12, 2026-10-14):** a full projection and the full builds of credentials, address types, area counts and record quality, and the Medicare enrollment and Part D prescriber loads, drop the plain secondary indexes of their empty staging tables and add them back in one `ALTER` per table after the fill (`DeferredIndexes`; `TableSwap.ReplaceAsync(…, deferIndexes: true)`). Kept during the fill: the primary key, unique indexes, indexes starting with `npi` (later fill steps join by NPI), FULLTEXT (adding one rebuilds the table: provider_org_name 200 s afterwards, 83 s for the fill with it) and SPATIAL (the map build was slower with it added afterwards, so the map tables defer nothing). Incremental builds write into tables that already hold data and are unchanged.
- **Incremental (2026-10-13, migrations 089–090):** the loads queue the NPIs whose raw data changed in `projection_pending`: a weekly's NPIs (after dropping its older rows), a monthly's differences before the swap, in the columns the projection reads only (`ProjectionBuilder.ReadsColumn`, found in its own SQL; a test changes every other column and checks the projection is unchanged): npidata rows by `Source_Hash` (090: MD5 of those columns as in the file, written by LOAD DATA while each weekly or monthly streams in), other names, practice locations and endpoints by an MD5 per NPI; the deactivation flags and report-filled dates are carried over first, so the ~357,000 deactivated NPIs don't look changed. Comparing every column, by MD5 of both tables, took 21 min on the October 2026 file and found 4.6M NPIs that differed, in columns nobody shows (EIN, certification date …), and the NPIs whose deactivation flag or date changes (only those rows are written now). `run` and `project changed` then rebuild only the queued NPIs, with the same SQL into the staging tables, and replace their rows in the live tables in one transaction (`provider_search` rows found by their whole key; new AUTO_INCREMENT ids for the rebuilt rows); the change log compares the staging rows with the live ones. A first build, a queue over 10% of the providers (`IncrementalLimit`), an NPPES file loaded with nothing queued (before migration 089), or `project` without `changed` rebuilds everything. A reference reload (NUCC, HUD, Census) alone no longer rebuilds the projection: it only refreshes `data_version`.
- **Incremental builders (2026-10-13, migrations 091–092):** the incremental projection also queues its NPIs for the tables built on it (`builder_pending` per builder: credentials, address_types, areas, map; record quality in `quality_pending`) and, in the same transaction, keeps their locations and taxonomy codes as they were (`builder_old_location`, `builder_old_taxonomy`; the earliest state while an NPI is queued, a row with `is_primary = -1` marking a snapshotted NPI) and, per old location, the address label inputs (`label_input`: a suite or floor, an organization; 092). Only addresses where an (NPI, address, label inputs) row appeared or went are queued (`address_pending`, with the ZIP because `addr_key` has no index): a weekly re-saving 32,641 providers at addresses shared with 1.85M locations queues none. Each builder then replaces only those NPIs' rows, finding the old ones by their exact keys (`BuilderPending`): **credentials** (raw values new to `credential_map` mapped with the stored known credentials; a different known set, kept as a hash in `reference_data.version`, rebuilds everything; holders of a credential crossing the list's limit get their "Other" rows replaced), **address types** (the queued addresses relabelled; building_search replaced for the batch and for those at an address whose label changed), **area counts** (each NPI's contributions before and after compared and the difference added; the new providers' area rows worked out once into a scratch table and counted, ~1 min instead of ~8), **map** (the queued NPIs and everyone at an address geocoded or placed since its last update, `checked_at`; more than `MapBuilder.IncrementalLimit`, 10% of the providers, builds in full instead, speed item 17), **record quality** (the queued NPIs, those at an address whose map point or building label changed, and those whose last update crossed the 5- or 10-year limit because the as-of date moved). `reference_data 'projection'.loaded_at` is the last FULL projection (none recorded: the builders' own last full builds stand; `data_version.projected_at` moves with every build, so it is no stand-in); a builder whose own `loaded_at` (its last full build) is older rebuilds in full, as do the areas after a NUCC or HUD reload; incremental updates move only `checked_at`. The `credentials`, `areas`, `address-types` commands, a FEMA load and `overture` for every state rebuild in full; `project` without `changed` rebuilds everything. A test checks that every builder takes its incremental path and gives the same tables as a full rebuild. **Side by side (speed item 13, 2026-10-15):** after the projection, the standardized credentials, address types and area counts read none of each other's tables, so `run`, `project` and `sample` build them at once (`BuilderSteps`, `ParallelBuilders` default 3; 1 = one after another), each on its own connection; a failed builder doesn't stop the others, and one that loses a deadlock or lock wait timeout starts again once. The map, FEMA, record quality and the full export follow in order. The snapshot cleanup (`BuilderPending.CleanAsync`) runs after each builder's commit, in a READ COMMITTED transaction of its own, one at a time (user lock `builder_clean`; inside the builders' transactions it locked the snapshot rows the others read), and the incremental projection cleans up before it snapshots. **`provider_map_credential` is filled once:** in `run`/`sample` a full credentials build leaves it owed to the map (`reference_data 'provider_map_credential'` deleted), and the map fills it with its points, or on its own after an incremental update; an incremental credentials build adds no cells for NPIs queued for the map. The `credentials` and `project` commands keep it current themselves. The credential builder takes the map's lock.
- **Dataset reloads queue too (2026-10-13):** when `TableSwap` replaces a table the record quality reads per NPI (`QualityBuilder.QueuedTables`: Medicare utilization and Part D (the older Medicare years queue per year, `MedicareHistorySource`), Care Compare clinicians and their locations, enrollment and reassignment, revalidation, order and referring, MIPS, facility affiliations and enrollments, equipment suppliers, opioid treatment programs), it first compares the new rows with the current ones per NPI (`NpiRowDiff`: an MD5 per NPI over its rows' MD5s, the same comparison a monthly uses for the NPPES child tables) and queues the NPIs that differ in `quality_pending`; those sources (`QueuedInputs`, with the state licenses) then relabel only the queue. Open Payments years (the newest two years shift together), the Provider of Services and Overture listings (matched by address) and full map or address type builds still relabel everyone, as does a queue over 10% of the providers (`QualityBuilder.IncrementalLimit`).

### Stage 1 — C# loader (done)
Commands (`Npi.Loader <command>`): `run` (default), `migrate`, `discover`, `load-file <zip>`, `reference`, `project`; since Stage 5.5 also `datasets`, `credentials`, `address-types`, `quality`, `areas`, `geocode` and `overture` (§7 Stage 5.5); since 2026-10-15 `directories` (the facility and group directory tables), `area-history [full]` (the monthly area figures; with `full`, every provider's locations compared) and `history [yyyy-MM | discover | measure <zip>…]` (the NPPES history from the archived monthly files, §7 Stage 5.5 "History before October 2026"); since 2026-10-16 `org-groups [measure [csv]]` (the organization groups of the combined profiles, §7 Stage 5.5 "Combined organization profiles"; `measure` groups in memory only, changes nothing, and can write every member to a CSV); since 2026-10-14 `doctor` (checks this computer's setup and says what to fix; changes nothing) and `sample` (the newest weekly file only, the reference data and the tables built from them, for a quick try; the weekly is recorded as `Sample`, not Completed, so a later `run` loads the monthly and then that weekly again). `publish` belongs to the old Stage 6 design and exits 1 "not implemented".

1. **Discover:** `HttpClient` GET of `NPI_Files.html`. Hrefs are classified by regex, V2 only:
   - `^NPPES_Data_Dissemination_(?<month>[A-Za-z]+)_(?<year>\d{4})_V2\.zip$` → monthly
   - `^NPPES_Data_Dissemination_(?<from>\d{6})_(?<to>\d{6})_Weekly_V2\.zip$` → weekly
   - `^NPPES_Deactivated_NPI_Report_(?<date>\d{6})_V2\.zip$` → deactivation

   Anything else is logged and ignored. Order: the newest unprocessed monthly, then the weeklies chronologically, then the newest deactivation report. Only the newest monthly and the newest report are loaded.
2. **Bookkeeping:** a file counts as done only when `downlog.status = 'Completed'`, so failed or partial files are retried. All SQL is parameterized.
3. **Download:** streamed to `WorkFolder` under a temp name, renamed on success, and the zip is verified to open. Retries with backoff (`DownloadAttempts`). Never reports success on failure. `KeepLastZip` keeps the newest zip. Files of at least `DownloadPartMinBytes` (64 MB) from a server that accepts byte ranges are fetched in `DownloadParts` (4) ranges at once (`HttpFileFetch`, with `If-Range` so a file that changes meanwhile is never put together from two versions; 2026-10-13; parts only with a strong ETag or a Last-Modified date). A part answered with a server error, 429 or a cut-off connection is asked again (3 tries, 2 s then 4 s); a part answered with the whole file (200: the server ignored the range, as data.nber.org does under load, or the file changed) or one that keeps failing makes that attempt download the whole file again in one stream, from scratch and with the new response's validators, logged in one line (2026-10-15). Dataset files are deleted only after a successful load (`WithDownloadAsync`, Medicare enrollment); a kept file is reused when the server answers 304 to `If-None-Match` / `If-Modified-Since` with the validators saved beside it (`<file>.download.json`), so a retried 9 GB Open Payments load doesn't download again.
4. **Bulk load:** each CSV is streamed straight from the zip entry into `MySqlBulkLoader` (`SourceStream`, `Local = true`), with the column list taken from the header row (§4), into a staging table. Dates and empties are converted in SQL, never by rewriting the CSV (defects #1, #2).
   - `MySqlBulkLoader` can't emit `ESCAPED BY ''`, so the escape character is **U+0001**, which never occurs in NPPES text; a backslash fixture test guards this.
   - Values load into user variables (`SET col = NULLIF(@c0, '')`); DATE columns use `STR_TO_DATE(…, '%m/%d/%Y')`.
   - `LOAD DATA LOCAL` downgrades errors to warnings, so **any warning fails the load**.
5. **Monthly full:** `npidata`, `other_names` and `practice_locations` load into `*_staging`. After the ≥ `MinRowRatio` (95%) check, they are swapped in atomically with one RENAME (defect #11).
6. **Weekly:** upsert into `npidata` only where the incoming `Last_Update_Date` ≥ the stored one (compared as dates; defect #9). Other names and practice locations of those NPIs are replaced. One transaction.
7. **Deactivations:** ExcelDataReader reads the report; data starts at the first row whose first cell is a 10-digit NPI (defect #6). The report is the full list, so it **replaces** the table (staging + RENAME, ≥ 95% check), then flags follow §6.1.
8. **`local_infile`:** the loader never runs `SET GLOBAL`. It checks `@@local_infile` and fails with instructions for `my.ini` if it's off.
9. **Logging and exit codes:** a Serilog rolling file `getnpidata-YYYYMMDD.log` in `LogFolder`, kept 60 days, with a summary line per file (rows, duration). Exit code 0 = all completed, 1 = something failed, 2 = bad command line.
10. **Parity:** the VB loader couldn't run on the loader PC, so parity was checked against the VB-loaded data restored from the owner's backup (§12, Stage 1). `legacy/` was deleted afterwards.

Configuration order: `appsettings.json` → `appsettings.Local.json` → user-secrets (loaded in every environment, so a scheduled run outside Development still finds them) → environment variables with the prefix `NPI_`.

### Stage 3 — Search projection + `Npi.Core` search service (done)
1. **Projection:** `project` builds the §6.2 tables:
   - the 15 taxonomy slots are unpivoted, skipping blanks;
   - locations are the primary practice address plus each `practice_locations` row, with zip5/zip4 normalized;
   - deactivated NPIs are excluded, and `row_hash` is computed.
2. **`SearchFilter`:** Classification, Specialization, TaxonomyCode, State, CountyFips, City, Zip5, RadiusMiles, LastName, FirstName, OrgName, Npi, EntityType, Gender, Credential, Sort, Page, PageSize.
3. **SQL builder (`SearchQuery`):** parameterized only; the sort whitelist is `name|npi|credential|city|state|zip|lastUpdate|enumeration`, and a `-` prefix means descending.
   - **Specialty:** `TaxonomyCatalog.ResolveAsync` maps Classification/Specialization to taxonomy codes, cached hourly.
   - **Location:** **any** location of the NPI matches. County = `zip5 IN (zip_county for the FIPS)`. Radius = a bounding box on `zip_centroid`, then haversine. City (owner, 2026-10-11) = the name as written **or** a ZIP USPS gives that name (`zip_county.usps_city`, in the state), so misspellings in NPPES are found; `SearchService` looks the ZIPs up first and passes them as a list, and with a state the city condition carries it (`(state AND city) OR zip5 IN list`, no separate state condition on provider_location), so MySQL merges the (state, city) and (zip5) ranges: NY + Saint James 4 s → 0.03 s; the search tables keep the state condition.
   - **Names:** prefix match (`LIKE x%`), wildcards escaped, no leading wildcards.
   - **Driver:** the most selective filter becomes a derived table of candidate NPIs, and MySQL is pinned to start from it with `/*+ JOIN_ORDER(c, p) */`. Priority: NPI → specialty + location (`provider_search`) → specialty (`provider_taxonomy`) → name prefix → location (`provider_location`) → credential. The other filters check the candidates. Without the pin, MySQL scanned the whole `sort_name` index to satisfy `ORDER BY … LIMIT`.
   - **Queries:** first, the page's NPIs with the total via `COUNT(*) OVER ()`; a separate count runs only for a page past the end. Then, per NPI: the matching location (primary first), the county name (the filtered county, else the ZIP's largest-share county) and the primary specialty. `SearchAllAsync` streams every match for CSV.
   - **Broad searches** (§11 item 6): location-only searches are counted first, without a join. At ≥ 200,000 matches (`BroadSearchThreshold`), the page walks the sort index (`FORCE INDEX FOR ORDER BY`, with `NO_SEMIJOIN` on the location EXISTS).
4. **Validation (`SearchValidation`):**
   - No filter is required (owner, 2026-10-14): none lists every active provider (§7 Stage 5.5 "Nationwide lists").
   - NPI 10 digits, ZIP 5 digits, radius 1–100 miles (needs a ZIP with a centroid), page size 1–200.
   - Text filters at most 60 characters.
   - Paging stops at 10,000 rows (`MaxResultWindow`; use the CSV beyond that).
   - A 30 s search timeout (`SearchTimeoutSeconds`); past it the user is told the search is too broad and to add a filter or download the CSV.
5. **Performance target:** < 2 s for "Classification + county" and "Classification + state" on full data. **Met** (§12): Chiropractor + Suffolk 0.27 s, Chiropractor + NY 0.08 s.

## 9. Conventions & guardrails

- C# 14 (the net10.0 default), nullable enabled, warnings as errors in `src/`. Async all the way down, with a `CancellationToken` everywhere in the loader and web.
- **All SQL parameterized.** Table and column identifiers come only from whitelists or the validated header mapping, backtick-quoted.
- Never run destructive SQL (TRUNCATE/DROP/RENAME, mass DELETE) against anything but the throwaway `npi_test_it_*` test databases without the owner's explicit OK. Production (`workplace`, Azure) changes go through migrations and the loader only.
- **Never edit an applied migration** (its checksum is verified); add a new numbered one.
- Tests: every defect class in §3.2 has a regression test using `tests/fixtures`. Integration tests read `NPI_TEST_MYSQL` and are skipped when it's not set; CI sets it (MySQL in Docker).
- Don't download the 1.1 GB monthly file in tests. Use fixtures, or a weekly file (~7 MB) for manual end-to-end runs.
- Keep this file and README.md current. If a decision changes, a fact turns out wrong, or a capability is added, fix it here (and in README.md if users see it) in the same commit.
